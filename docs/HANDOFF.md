## Open deviations from the main doc

*(Implementation choices that differ from or refine the spec, not yet folded back into the main doc. Each entry: what changed, why, and which part/section of the main doc it affects. When the founder folds one into the main doc, move it to the session log entry where the fold happened.)*

- **`World` still has no fixed named vocabulary — resolved differently than Part 3's wording implies.** M2's generic `knob(name)` mechanism is now genuinely exercised: Botanical declares 11 real knob names via `worldKnobs()` (`hueBase`, `hueSpread`, `branchDensity`, `baseGrowthRate`, `matureDurationMs`, `windAngle`, `rootCount`, `branchSpreadBase`, `wanderAmplitudeBase`, `blossomsPerCluster`, `subBranchSpawnChance`). `World` itself still carries no fixed field list — each style privately owns the meaning of its own knob names. This satisfies the spec's actual requirement ("adding a new knob later leaves every existing world unchanged") without `World` ever needing a shared vocabulary; a second style (M6) will declare its own, unrelated knob names against the same mechanism. Affects Part 3, "The seed system." No fold expected unless the founder wants a shared cross-style knob vocabulary (e.g. every style must have *some* palette knob) rather than each style defining its own.
- **Compositor: the export path stays a single depth-sorted full-redraw loop; the LIVE preview path now does real per-layer persistent canvas buffering (session 013) — narrowing, not closing, this deviation.** Part 3 names "an ordered stack of layer canvases... each layer independently chooses accumulate or clear-and-redraw" as Botanical's resolution mechanism. Through session 011 this was resolved entirely inside `botanical.ts`'s own state (elements simply persist and get re-emitted every tick) with the compositor itself staying one clear-and-full-redraw pass — deliberately simpler than real persistent-canvas buffering, on the theory that a few hundred to low-thousands of draw calls per frame is trivial for Canvas 2D. **That theory turned out to be wrong at session length**: a real long-session performance problem showed up in practice (frame rate collapsing from 58fps to 5.7fps over 3 minutes, discovered during session 012's live testing — see the session 013 log entry for the fix). Session 013 built the real per-layer persistent buffering Part 3 originally called for, but scoped ONLY to the live on-screen preview (`src/compositor/live-compositor.ts`, wired into `src/app/live-render-loop.ts`) — `render-scene.ts`'s `renderScene()` itself is completely untouched and still does one clear-and-full-redraw pass. **Correction, session 015: session 013's claim that this makes the export "byte-for-byte untouched" was based on an incorrect assumption about how export actually works, caught while investigating the paint-order bug below.** `renderScene()` is never actually called at session-end in the real app — `main.ts`'s `saveSession()` calls `exportCanvasAsPng(canvasEl, ...)` (`src/storage/image-export.ts`), which is just `canvas.toBlob()` on the *same live on-screen canvas* the `LiveCompositor` paints into every frame. So a live-compositor rendering bug (like the paint-order one session 015 fixes) *does* affect the saved artifact, not just the transient on-screen animation — this was wrongly asserted otherwise in session 013's PR/handoff entry. `renderScene()` in its current, only-real capacity is used by the determinism tests and by any style that doesn't implement `sceneLayers()` (i.e., doesn't opt into the incremental path) — it does not independently regenerate the export. Affects Part 3, "Depth-layered rendering," and this doc's own session 013 entry (left as historical record below, not rewritten, per this doc's own newest-first/append practice — this correction is the authoritative update). No fold expected — this is a documentation-accuracy fix, not a new deviation — but worth remembering: the live path and the export path are the same pixels, so bugs there are equally consequential to both.
- **Palette selection is a founder-facing UI choice, not just a seed-random draw.** Part 2 says "style-level choices now, palettes later" without specifying *when* "later" is. Mid-M4, the founder asked for palette choice now (a default plus 2 curated presets, switchable via the UI, full custom color-wheel picking deferred as explicitly-acceptable-for-v1). Implemented as `hueBase`/`hueSpread` knobs (replacing an earlier single-hue design) plus 3 named preset override bundles (`src/styles/botanical/palettes.ts`) applied via `World`'s existing per-knob override mechanism — no new World machinery needed — and 3 buttons in `main.ts` that restart the live loop with the chosen preset. Affects Part 2's "Design decisions made" section. Fold candidate: promote "palette choice now" from an open question to a stated v1 decision.

Affects Part 3's fixed-timestep paragraph and Part 4's M5 milestone description. Fold candidate: M5 should build directly on `live-render-loop.ts` rather than re-deriving the live-tick-pump logic.

### Session 018 — 2026-08-23 — Real before/after comparison finds two more real bugs (PR #16 continued)

**Goal this session:** the founder tested session 017's fix live, reported the bug still happening (a second recorded video, "example of bug still happening.mp4"), and explicitly asked whether the coordinator was "just guessing" — pushing for a real comparison between the old (pre-PR #13 performance refactor) and current rendering instead of another hypothesis-first pass. ### Session 015 — 2026-08-23 — Live-compositor paint-order bug (branches "poof disappearing")

**Goal this session:** after PR #12 merged, the founder reported a new bug while continuing to use the app: branches that had been drawn would sometimes vanish, and blossoms would sometimes appear in a sudden burst instead of gradually. **Investigation (extensive, several dead ends worth recording so a future session doesn't re-walk them):**
- First hypothesis (wrong, but worth the ~30 minutes it took to rule out with confidence): a stroke's per-kind bake-tracking index could become unstable if a not-yet-qualifying branch (segments.length still 1) started qualifying at an array position *between* two already-baked branches, shifting their apparent indices. Traced through the actual tick/spawn mechanics in `branch.ts`/`botanical.ts` in detail and proved this is structurally impossible: `system.branches` is strictly append-ordered by spawn time, and every growing branch gains exactly one segment per tick it's processed, so an older (lower-index) branch can never have fewer segments than a younger (higher-index) one at any observed frame. Ruled out.
- Four independent live/Node diagnostics, each targeting a different layer where data could theoretically be lost, all came back clean: (1) a 3-minute headless Node test stepping Botanical's internal state directly — branch/blossom counts only ever grew; (2) `scene()` vs `sceneLayers()` element-count agreement checked at every 10-tick checkpoint over 70 seconds — always identical; (3) instrumented `bakeLayer` to log whenever a layer's "already baked" count fell behind its "should be baked" count, across every growth system, over a 70-second live session — zero mismatches; (4) read raw pixel data directly out of the persistent buffer canvases (bypassing the visible canvas and its own compositing), across multiple live runs — non-transparent pixel counts only ever grew. This conclusively ruled out actual data loss anywhere in the pipeline — branches, blossoms, and buffer pixels were never actually being erased.
- Tried a fake-webcam repro (`chromium.launch({ args: ['--use-fake-device-for-media-stream', ...] })`) to test the real camera/pose-detection timing path, since all prior repros used the synthetic slider adapter — dead end: Chromium's fake device shows a generic test pattern with no person in it, so MediaPipe never detects a pose and nothing grows at all. Not useful without a stand-in video of an actual person, which wasn't available.
- The actual breakthrough came from asking the founder for more specific detail rather than continuing to guess blind: **"it happened when it's the first frame-ish, before the canvas expands, and a BUNCH of blossoms appear at once, and then once the canvas scrolls past that it functions as expected"** — and, critically, **"it also happens with the sliders,"** confirming this doesn't need a real camera to reproduce.

**Root cause:** the live-compositor (`src/compositor/live-compositor.ts`, from session 013) bakes each newly-finished element onto a persistent canvas buffer permanently, in whatever order it happens to become bakeable — *not* in depth (z) order. The old full-redraw renderer (`render-scene.ts`'s `renderScene`) always re-sorts every element by z fresh, every single frame, so paint order is always depth-correct there; the new baking compositor draws once and never revisits, so a wrong-order bake stays wrong forever. This mostly doesn't matter once growth has spread out across a wide canvas (different branches rarely overlap on screen) — but early in a session, **before the canvas has expanded past its initial width, everything is crammed into the same small area**. Botanical can spawn 2 root branches (`rootCount` lands in `{1, 2}`), and `z = clamp01((i + zJitter) / rootCount)` (`initGrowthSystem`) puts root 0 around z≈0–0.5 and root 1 around z≈0.5–1 — genuinely different depths, but both start bunched together near the left edge. Whichever finishes baking later (maturing, or revealing a dense blossom cluster) permanently paints over the other's screen area regardless of correct depth, which looks exactly like the first one vanishing — and matches "peters off after a while" exactly, since once growth spreads out, different-depth branches stop overlapping on screen and the bug stops manifesting.

**Fix** (one Sonnet builder, contract pinned first, branch `fix-bake-depth-order`): `bakeLayer` replaced with `collectAndBakeBucket`, which operates across *all* layers sharing one depth bucket at once, per frame: collect every newly-bakeable element (newly-final strokes, newly-appeared circles) into a list *without* drawing yet, sort the whole batch by `z` descending (farthest first, matching `renderScene`'s own convention exactly), draw in that order, and only *then* commit each layer's bake-state bookkeeping. This changes nothing about *what* gets baked or *when* — only the paint order among elements that become bakeable in the same frame. Independently re-read the diff against the pinned contract before accepting it (matches exactly) and confirmed the new tests are non-vacuous: two elements from different layers with different z, tested with both possible array orderings, must always paint farthest-first regardless of which layer is listed first — proving it's not an array-order coincidence.

**A real correction found while investigating, unrelated to the fix itself but important:** session 013's PR/handoff claimed the session-end export was "byte-for-byte untouched" because `renderScene()` itself wasn't modified. That's true but misleading — `renderScene()` is never actually *called* at export time in the real app; `main.ts`'s `saveSession()` just screenshots the live on-screen canvas directly (`exportCanvasAsPng(canvasEl, ...)`), the same canvas the `LiveCompositor` paints into every frame. So a live-compositor bug (like this one) affects the saved artifact too, not just the transient on-screen animation — corrected in the "Open deviations" compositor entry above.

**A real correctness bug found during independent review, before any live testing — worth recording in detail since it's the kind of thing that would have shipped invisibly otherwise:** the first builder round baked each stroke segment the instant it was appended, using whatever `points.length` the branch had at that moment (`drawStrokeSegment`'s taper formula is `t = i / (points.length - 1)`, thick at `t=0`, thin at `t=1`). Since a segment is always newest — closest to the tip, so `t≈1` — the instant it's baked, nearly every segment would freeze at a "thin, near-tip" width and never get the chance to visually thicken as the branch kept growing past it, the way the old full-redraw-every-frame path did (it recomputed every segment's taper fresh each frame using the CURRENT running point count, converging to the correct final width only once a branch matures and its point count stops changing). Traced through concrete numbers to confirm before sending it back: a segment baked at points.length≈11 gets `t≈0.9`; once that branch reaches its true final length of 100 points, that same segment's correct `t` is ≈0.1 — night-and-day different widths. In practice this would have made every branch in the live preview render as a uniformly thin wire instead of the intended thick-root/thin-tip taper, for the entire length of every branch, the whole session — not a subtle edge case. Sent back to the same builder with a precise fix: only bake a stroke once it's `final` (a new `StrokeElement.final?: boolean` field, `true` once `branch.lifecycle === 'mature'` — confirmed via `branch.ts` that `tickGrowing` never touches a branch's `segments` again after that point, so "mature" and "this points array is permanently done growing" are exactly the same condition), baked whole in one shot at its true final point count (matching `renderScene()`'s own math exactly). While still growing, a stroke isn't baked at all — it's redrawn fully, fresh, every frame, directly onto the destination canvas, cheap because concurrently-growing strokes are a small bounded set (capped by `maxConcurrentBranches` per system), unlike the unboundedly-accumulating mature content that was the actual problem. This also required a paint-order fix: a bucket's still-growing strokes must be drawn after that bucket's own persistent-buffer blit but before the next (nearer) bucket composites over them — not all lumped at the very end, which would let a still-growing echo (background) branch incorrectly paint over already-composited foreground content.
