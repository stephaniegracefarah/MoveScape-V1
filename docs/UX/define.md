# Define — Problem Statement

*2026-08-23. Output of the Define phase (see `UX_PLAN.md`). Input: `discover-findings.md`'s five synthesis themes only.*

## Clustering the Discover themes

Discover's five themes cluster into three underlying issues:

**A. Process/mechanism visibility** (themes 1 and 2) — whether and how MoveScape shows its own generative mechanism at work (the movement readout, the seed/determinism system) is currently a default (mostly hidden), not a deliberate choice. Live-coding culture and the generative-art tradition both suggest visibility can be a genuine strength, not a flaw to be designed away.

**B. The session lifecycle** (themes 3 and 4) — how a session begins, sustains itself, and ends is currently whatever engineering milestones produced (start → move → Finish → binary Save/Discard), not a considered design. The closest direct analog (Eno's *Reflection*) takes the opposite approach entirely, and the closest adjacent-domain analog (Midjourney) offers more than two paths at the decision point.

**C. No external scaffolding** (theme 5) — unlike every gallery-installation analog, MoveScape has no room, attendant, or physical context doing trust-building and expectation-setting for it. The page carries that weight entirely alone.

## Problem statement

> Because MoveScape has no physical space, attendant, or context to lean on the way a gallery installation does, the page itself must deliberately decide — not default into — how visibly it shows the mechanism turning movement into art, and how a session begins, sustains itself, and ends. Right now, neither decision has actually been made on purpose; both are accidents of engineering-milestone order.

## User-need statement

> As someone opening MoveScape to make art through movement, I need the page to make confident, legible choices about how the process is shown and how a session unfolds, so that watching my movement become art feels intentional — not like an unfinished engineering interface I have to look past.

## Success criteria (page/product UX only)

1. **Process visibility has a stated decision, not a default.** Whether (and how) the movement-tracking mechanism is shown during a session is an explicit choice, argued for one way or the other — not simply whatever the engine's dev tools happened to expose.
2. **The session lifecycle has a stated decision, not a default.** How a session starts, whether/how it can continue past a single "keep or discard" moment, and how it ends are each a deliberate design choice — not just whatever milestone order produced.
3. **The idle/first-load state builds trust and sets expectations using only what's on the page.** No reliance on prior context, external explanation, or the user already knowing what MoveScape is.
4. **No two adjacent controls of different consequence look the same.** (E.g., a routine action and a destructive one should never be visually identical and next to each other.)
